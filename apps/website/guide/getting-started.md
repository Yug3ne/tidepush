# Getting started

This tutorial takes you from nothing to an OTA update running on a real phone, then rolls it back. Do the steps in order; each one builds on the last.

It uses **Android** because you can install a release APK directly on a phone. iOS works the same way; the differences are noted where they matter.

**Time:** about an hour the first time.

## What you need

| Thing | Why | Check |
| --- | --- | --- |
| A **Cloudflare account** (free) | Tidepush runs there | Sign up at [dash.cloudflare.com](https://dash.cloudflare.com) |
| A **payment method** on that account | Cloudflare asks for one to turn on R2, even for the free allowance | Dashboard → R2 |
| **Bun** 1.1 or newer | Runs the CLI and installs dependencies | `bun --version` |
| **Node.js** 20 or newer | Expo's tools (`npx expo …`) need it | `node --version` |
| **Git** | To clone the repository | `git --version` |
| An **Expo app** (SDK 50+) that uses **prebuild / CNG** | The app you will update | It has an `app.json` or `app.config.ts`; `android/` and `ios/` are generated by `npx expo prebuild` |
| **Android build tools** (Android Studio, JDK 17) and an Android phone with USB debugging, or an emulator | To build and install a release APK | `adb devices` lists your phone |

::: info "CNG" / "prebuild"
Continuous Native Generation means you don't edit `android/` and `ios/` by hand; Expo generates them from your app config with `npx expo prebuild`. Tidepush doesn't strictly require it, but this tutorial assumes it, because then every setting lives in `app.json`.
:::

Throughout the tutorial:

- `~/tidepush` is where you clone Tidepush,
- `~/my-app` is your Expo app,
- `<your-subdomain>` is your workers.dev subdomain (you'll see it in step 3).

## 1. Clone and install

```sh
git clone https://github.com/Yug3ne/tidepush ~/tidepush
cd ~/tidepush
bun install
```

**What just happened:** you downloaded the server, the dashboard and the CLI, and installed their dependencies (including Wrangler, Cloudflare's CLI) into `node_modules`.

## 2. Generate code-signing keys

Code signing makes sure your app only runs updates that came from you. You create a key pair once:

- a **private key**: stays secret, goes to Cloudflare as a Worker secret, and is used to sign updates;
- a **certificate**: public, goes inside your app, and is used to check signatures.

First install `expo-updates` in your app (you'll configure it in step 6):

```sh
cd ~/my-app
npx expo install expo-updates
```

Then generate the keys. This puts the **certificate in the app** and the **private key outside the app**, in Tidepush's `.secrets` folder, which Git ignores:

```sh
cd ~/my-app
npx expo-updates codesigning:generate \
  --key-output-directory ~/tidepush/.secrets/codesigning-keys \
  --certificate-output-directory certs \
  --certificate-validity-duration-years 10 \
  --certificate-common-name "My App"
```

You now have:

| File | What it is | Where it belongs |
| --- | --- | --- |
| `~/my-app/certs/certificate.pem` | Public certificate | **Commit it** to your app repository. It's built into the app. |
| `~/tidepush/.secrets/codesigning-keys/private-key.pem` | **Private key** | **Never commit it.** Store it in a password manager. It becomes a Cloudflare secret in step 3. |
| `~/tidepush/.secrets/codesigning-keys/public-key.pem` | Public key | Not needed by Tidepush. Keep it with the private key. |

::: danger Never commit the private key
Anyone with the private key can sign updates that your users' phones will accept and run. If it leaks, you have to make a new key **and ship a new store build** with the new certificate. See [Code signing & keys](/guides/code-signing).
:::

## 3. Deploy to Cloudflare

### 3a. Log in with Wrangler

```sh
cd ~/tidepush/apps/server
npx wrangler login
```

A browser window opens. Allow access. Back in the terminal you'll see `Successfully logged in.`

### 3b. Turn on R2

R2 must be enabled once per account in the Cloudflare dashboard: **Storage & databases → R2 → Purchase R2 / Enable**. The free allowance is 10 GB; you won't be charged unless you go over it.

Then create the bucket that stores your bundles and images:

```sh
npx wrangler r2 bucket create tidepush-assets
```

Expected output ends with:

```text
✅ Created bucket 'tidepush-assets' with default storage class of Standard.
```

::: warning "Please enable R2 through the Cloudflare Dashboard"
If you see this error, step 3b's dashboard part isn't done yet. Enable R2, then run the command again.
:::

### 3c. Deploy the Worker

From the repository root:

```sh
cd ~/tidepush
bun run deploy
```

This builds the dashboard and deploys the Worker. On the first deploy, Wrangler also **creates the D1 database** named `tidepush` for you. If you have never used Workers before, Wrangler may ask you to pick a **workers.dev subdomain**; choose any name.

At the end you'll see something like:

```text
Deployed tidepush triggers
  https://tidepush.<your-subdomain>.workers.dev
```

That URL is your **server URL**. Save it:

```sh
export TP_URL=https://tidepush.<your-subdomain>.workers.dev
```

### 3d. Create the database tables

```sh
cd ~/tidepush/apps/server
npx wrangler d1 migrations apply tidepush --remote
```

Wrangler lists the migrations (`0001_init.sql`, `0002_auth.sql`, …) and asks `Ok to proceed?`. Answer `y`. Each one should show ✅.

**What just happened:** the D1 database now has its tables (updates, assets, devices, admins, sessions, …). `--remote` means "on Cloudflare", not on your laptop.

### 3e. Add the secrets

The Worker needs two secrets.

**`CODE_SIGNING_PRIVATE_KEY`**, the key from step 2:

```sh
cd ~/tidepush/apps/server
npx wrangler secret put CODE_SIGNING_PRIVATE_KEY < ../../.secrets/codesigning-keys/private-key.pem
```

**`SETUP_TOKEN`**, a one-time password that protects the "create the first account" page:

```sh
SETUP_TOKEN=$(openssl rand -hex 32)
echo "Your setup token: $SETUP_TOKEN"
echo "$SETUP_TOKEN" | npx wrangler secret put SETUP_TOKEN
```

Copy the printed setup token somewhere safe for the next step. Each `secret put` prints `✨ Success! Uploaded secret …`.

### 3f. Check it's alive

```sh
curl $TP_URL/health
```

```json
{"ok":true}
```

Ask it for an update the way a phone would:

```sh
curl -i "$TP_URL/manifest" \
  -H "expo-protocol-version: 1" \
  -H "expo-platform: android" \
  -H "expo-runtime-version: test" \
  -H "expo-channel-name: production"
```

You'll get `HTTP/2 200` with `content-type: multipart/mixed` and a body containing `{"type":"noUpdateAvailable"}`. Nothing is published yet, so that's correct.

## 4. Create the first owner account

Open your server URL in a browser. Because there are no accounts yet, you're sent to **`/setup`**.

Fill in:

- **Setup token**: the value from step 3e,
- your **name**, **email**, and a **password** (12 characters or more).

Submit. You're now signed in as the **owner**, and you'll see the (empty) Updates page.

::: tip Setup closes itself
Once an owner exists, `/setup` is closed for good. Invite teammates from **Settings → Team** instead. You can delete the `SETUP_TOKEN` secret now if you like: `npx wrangler secret delete SETUP_TOKEN`.
:::

## 5. Create an API token and configure the CLI

The CLI doesn't use your password. It uses an **API token**.

1. In the dashboard, go to **Settings → API tokens**.
2. Create a token named, for example, `my-laptop`.
3. Copy the token (it starts with `tp_`). **It is shown only once.**

Create a file called `.env` in the Tidepush repository root. Bun loads it automatically, and Git ignores it.

```sh
# ~/tidepush/.env
TIDEPUSH_SERVER_URL=https://tidepush.<your-subdomain>.workers.dev
TIDEPUSH_API_TOKEN=tp_paste_your_token_here
TIDEPUSH_APP_DIR=/home/you/my-app
```

`TIDEPUSH_APP_DIR` must be the **absolute path** to your Expo app.

Check it works:

```sh
cd ~/tidepush
bun run tidepush list
```

```text
No updates.
```

If you see `401` instead, the token is wrong or was revoked.

## 6. Configure the Expo app

Open `~/my-app/app.json` and add (or change) these keys inside `"expo"`:

```json
{
  "expo": {
    "runtimeVersion": { "policy": "fingerprint" },
    "updates": {
      "url": "https://tidepush.<your-subdomain>.workers.dev/manifest",
      "enabled": true,
      "checkAutomatically": "ON_LOAD",
      "fallbackToCacheTimeout": 0,
      "requestHeaders": { "expo-channel-name": "production" },
      "codeSigningCertificate": "./certs/certificate.pem",
      "codeSigningMetadata": { "keyid": "main", "alg": "rsa-v1_5-sha256" }
    }
  }
}
```

What each line does:

| Key | Meaning |
| --- | --- |
| `runtimeVersion.policy: "fingerprint"` | The runtime version is a hash of your native code. It changes by itself when native code changes, so an update never lands on a build it can't run. |
| `updates.url` | Your server's `/manifest` address. Note the `/manifest` at the end. |
| `checkAutomatically: "ON_LOAD"` | Check for an update every time the app starts. |
| `fallbackToCacheTimeout: 0` | Don't wait for the network at startup; start with what's on the phone and download in the background. |
| `requestHeaders["expo-channel-name"]` | The channel this build listens to. |
| `codeSigningCertificate` | The certificate from step 2. |
| `codeSigningMetadata.keyid` | Must equal the server's `CODE_SIGNING_KEY_ID` (default `main`). |

::: warning Don't run `eas update:configure`
That command points `updates.url` at Expo's servers. If you use **EAS Build**, also remove any `channel` field from your `eas.json` build profiles, because EAS writes it into the build's `expo-channel-name` header and it would override yours.
:::

Want separate staging and production builds? Add the optional `app.config.ts` + `fingerprint.config.js` from [Channels & promoting](/guides/channels). You can do that later.

Commit `app.json` and `certs/certificate.pem` to your app repository.

## 7. Build a release APK

`expo-updates` is **switched off in debug builds** (the ones with the Metro dev server). You must test with a **release** build.

```sh
cd ~/my-app
npx expo prebuild --clean
npx expo run:android --variant release
```

This builds a release APK and installs it on the connected phone or emulator. (Expo's Android template signs release builds with a debug keystore, so you can sideload them. That's fine for testing; use your real keystore for the Play Store.)

On iOS, use `npx expo run:ios --configuration Release`.

Open the app once so you know what it looks like now.

::: danger Build first, then publish
A phone ignores any update that is **older than its build**. If you published an update earlier and then built the app, that update will never show up on this build. Always publish **after** the build you're testing.
:::

## 8. Publish your first update

Make a visible change in your app, for example change a heading's text. Save the file. Then:

```sh
cd ~/tidepush
bun run tidepush publish --channel production --platform android -m "My first OTA update"
```

You'll see:

```text
• Exporting android bundle(s)…
  (expo export output)
• Reading app config and runtime version…
  android  runtime 3f9c1a7e…  bundle 2.1 MB  14 assets
• Uploading 15/15 files (2.6 MB)…
✔ Published to production at 100% (group 7c1e0b52-3a1f-4e0b-9d55-4c5e9a0f1b2d)
  android  4f2a8e77-91c3-4b8a-a1d0-6e2b9c7f3a10
```

**What just happened:** the CLI exported your current code, worked out the runtime version (it must match the build you installed), uploaded the files to R2, and created an update on the `production` channel.

Now on the phone:

1. **Close the app completely** (swipe it away from recent apps) and open it. It starts with the old code and downloads the update in the background.
2. **Close it again and reopen.** You see your change.

Refresh the dashboard: the update now shows **1 device**.

::: tip Didn't work?
Go through [The app never picks up my update](/troubleshooting#the-app-never-picks-up-my-update). The usual causes are a debug build, a runtime version mismatch, or publishing before building.
:::

## 9. Roll it back

Use the **group id** from the publish output (or copy it from the dashboard):

```sh
bun run tidepush rollback 7c1e0b52-3a1f-4e0b-9d55-4c5e9a0f1b2d
```

```text
✔ android  4f2a8e77-91c3-4b8a-a1d0-6e2b9c7f3a10: devices will roll back to the embedded bundle
```

Close and reopen the app twice. The original text is back.

**What just happened:** this was the only update, so there was nothing older to republish. The server now answers the phone with a signed `rollBackToEmbedded` directive, and the phone goes back to the bundle built into the APK. If there had been an earlier update, Tidepush would have republished that instead. See [Rollbacks](/guides/rollbacks).
